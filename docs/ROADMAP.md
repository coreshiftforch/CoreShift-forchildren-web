### 進め方のきまり（全作業に共通）

- 作業ブランチを切って PR を出し、確認してから `main` に入れる。`main` に入れると、そのまま core-shift.jp に公開される。
- 文言を変えるときは、次の方針に照らす（代表の決定）。
  - ページの情報はできるだけ簡潔にする
  - 費用・単価の具体的な数字は書かない
  - 相談したら開催が確定するように読める文は載せない
  - 「機材を持って伺います」という表現は使わない
- 見た目の変更は、パソコン幅（1440px）とスマホ幅（390px）の両方で画面を確かめてから PR を出す。
- 新しいページ（トップ／施設・学校向け／保護者向け／企業・個人向け／お問い合わせ）は、GitHub Pages の Jekyll で組み立てている（#15）。
  - ヘッダーは `_includes/header.html`、フッターは `_includes/footer.html`、`<head>` と全体の枠は `_layouts/default.html` の1か所だけを直せばよい。
  - 各ページの先頭（`---` で囲んだ部分）に、題（title）・説明文（description）・メニューで強調する項目（nav: orgs / children / support / contact）を書く。
  - `site.css` の読み込み番号は公開のたびに自動で変わるので、手で上げなくてよい。
  - 手元で見るには Jekyll が要る（`python3 -m http.server` では共通部品が組み込まれない）。
  - ページ本文に `{{` や `{%` を書くと Jekyll の命令として読まれるので、使わない。
- ブレークポイント: サイズ3（PC）1301px以上 / サイズ2 〜1300px / サイズ1（スマホ）〜768px。

## GitHub での分担の目安

- 1つの ID を1つの Issue にする。ラベル例: `確認`（A）、`デザイン`（B）、`素材待ち`（C）、`旧ページ`（D）、`SEO`（E）、`次回開催`（F）、`代表の判断待ち`。
- 同時に進めてよい組み合わせ: 触るファイルが違う作業どうし（例: B-2a と B-2c）。
- 同時に進めないほうがよい組み合わせ: `site.css` を大きく変える作業どうし（B-1b、B-3a など）、全ページを触る作業（B-3c、C-4、E-1）。
- 「代表の判断待ち」の Issue は、判断が出るまで手を付けない。
